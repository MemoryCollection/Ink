AccessibilityService 悬浮窗的 Z 序，在六台机器上跑了一遍

同一个 WindowManager.LayoutParams，同一个 TYPE_APPLICATION_OVERLAY，在一台机器上盖住了输入法，在另一台机器上被输入法盖住。这件事没有一个官方的答案，只能自己试。

问题从哪来

做群发助手的时候，需要在聊天界面上显示一个悬浮面板，告诉用户进度到哪了、还剩多久。面板必须压在所有东西上面，否则用户一滑就被挡住，然后以为卡死了。

Android 8.0 之后，TYPE_SYSTEM_OVERLAY 被废弃，官方推荐 TYPE_APPLICATION_OVERLAY。文档写得很清楚：它会显示在应用程序窗口之上，但会位于系统关键窗口（状态栏、输入法、锁屏）之下。

问题就在最后那句「之下」。

系统的定义是「应用窗口」，但每个厂商对「应用窗口」的理解都不一样。有的 ROM 把输入法算作系统窗口，有的算作应用窗口。

TYPE_APPLICATION_OVERLAY 不是银弹

我拿了六台机器做对照：Pixel 6（Android 14 原生）、小米 13（HyperOS）、一加 11（ColorOS）、vivo X90（OriginOS）、三星 S23（One UI），还有一台老的红米 Note 8（MIUI 11）。

测试方法很简单：在聊天界面弹一个悬浮窗，然后点输入框，看悬浮窗还在不在最上面。

厂商 ROM 的差异

小米和 vivo 把输入法算进了「系统关键窗口」，所以悬浮窗会被压下去。三星和一加则相反，悬浮窗会盖在输入法上，导致用户看不见自己在打字。

两种都很难受，只是难受的方式不同。前者让用户以为面板消失了，后者让用户没法输入。

一个可用的折中

最后的做法是：不跟输入法抢层级，而是监听输入法的可见性，在它弹出的时候主动把面板移走。

private fun watchImeVisibility(window: View) {
    val params = window.layoutParams as WindowManager.LayoutParams
    ViewCompat.setOnApplyWindowInsetsListener(window) { _, insets ->
        val imeVisible = insets.isVisible(WindowInsetsCompat.Type.ime())
        val imeHeight = insets.getInsets(WindowInsetsCompat.Type.ime()).bottom

        if (imeVisible) {
            // 把面板挪到输入法上方，留 12dp 呼吸空间
            params.y = -imeHeight - dp(12)
            windowManager.updateViewLayout(window, params)
        } else {
            params.y = 0
            windowManager.updateViewLayout(window, params)
        }
        insets
    }
}

这段代码在五台机器上表现一致，只有 MIUI 11 那台老红米还有问题——它的 imeHeight 偶尔返回 0。最后给了一个兜底：拿不到高度就按屏幕高度的 40% 估算。

还没解决的部分

分屏模式下，输入法高度和窗口位置的关系又变了，目前只能做到「不遮挡输入框」，做不到「面板始终在视野里」。这部分我先记着，等有精力再折腾。

记录这些不是为了给谁一个答案，是因为我在这上面花了大概两天，希望下一个人少花一天。
